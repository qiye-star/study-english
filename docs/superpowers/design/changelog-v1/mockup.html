设计要点和我的看法

点做法与理由
整页,不用弹窗日志会越写越长,需要滚动、分页和可深链接(以后可以从「我的」里再放一个入口)。这和跟读弹窗不矛盾:跟读是「做一件事」,日志是「读一份清单」。
结构化条目,不用 Markdown每条 = 类型标签 + 一句话。排版统一、双语好管、没有富文本注入;代价是不能放图片和长文。我认为更新日志用不着,真需要再加「详情链接」。
未读状态放服务端用一张很小的表记「每个用户读到哪一条」,这样手机、电脑之间同步;本机只缓存一份减少请求。若你更想要最省事,也可以只存在本机(换设备会重新亮红点)。
红点只算「已发布且比我读到的更新」草稿不出现;新用户首次登录不要把整份历史都算成未读,只显示最近 N 条为未读(默认 3 条)。
后端接口GET /api/changelog?cursor=(登录即可看,返回条目和 unread 数);POST /api/changelog/seen;管理端 /api/admin/changelog 增删改、发布 / 下架(审计)。内容公开,不含用户数据,日志里不记内容。
首批内容我可以根据最近的提交和你验证过的功能起草首批 5 到 8 条中英文日志,放进管理端当草稿,由你改完再发布;不会写进数据库迁移里。
不做推送通知、按用户或用户组定向、点赞评论、富文本图片、自动从 git 生成并直接发布。

需要你拍板

1入口只放在练习页顶栏(按你说的),还是也在「我的」里加一行?我推荐先只放练习页。
2日志页用整页(我推荐),还是底部弹窗?
3未读状态放服务端(我推荐,多设备同步),还是只存本机?
4条目要不要带「版本号」这个可选字段?我觉得可选就够,你的应用不一定需要版本号。
