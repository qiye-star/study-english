**Goal:** 管理员一次批量生成 ≤ 100 个一次性随机码(可设过期与标签,生成后只显示一次并可下载 CSV);每个满足条件的用户(注册满 7 天且邮箱已验证)可以生成**一个永久随机码**(不变、不过期、可多次使用,累计上限默认 10,可按人用配额覆盖调大 / 设为 0;本人或管理员可「更换」);每次兑换写 `invite_redemptions`(一个用户只能一条,是以后奖励 / 分成的归属依据);按 IP 的邀请码错误计数;分享链接把码放在 `#` 片段;网页「我的邀请码」面板;管理端批量生成、按种类 / 所有者筛选、兑换归属、每人的邀请状态与被停用数。

**Tech Stack:** 同 F 计划;不新增依赖。

## 明确不做(本期)

- **奖励、积分、付费、分成、返利、排行榜**:只记录「谁用了谁的码」,不触发任何后续逻辑(spec §6.2)。
- 自定义码、由用户 id 派生的码(spec §6.1 明确禁止:可预测)。
- 用户一次性码(spec 已由 A 方案改为 B 方案)。
- 邀请码兑换以外的归属来源(链接点击统计、UTM 等)。
- 被邀请者被停用时自动处理邀请者:只在管理端显示计数,人工判断。
- 用户码哈希改为带 pepper 的 HMAC(INDEX §5 建议,后续)。

## Global Constraints

- **邀请码是持有即可注册的凭据**:不进日志、错误体、审计、URL(只允许 `#` 片段)、测试快照与夹具;含码的响应带 `Cache-Control: no-store`;审计只写标签、计数、种类、所有者用户名。每个新端点 `caplog` 断言。
- 设置、迁移、路由顺序、分层、网页文案、主包预算(≤ 0.4 kB)、提交规则同 F 计划。
- 现有行为保持:`INVITE_CODE` 环境变量单码照常可用(无归属);现有管理员多次码(`POST /api/admin/invites`,`max_uses` ≤ 1000)照常可用;旧的 12 位码照常校验(X18)。

## 本计划的裁定(Ruling)

- **R-I1 数据**(迁移 `0024`):`invite_codes.kind String(8) NOT NULL DEFAULT 'admin'`(`server_default`,旧行即管理员码);`owner_user_id` FK `users.id` `ON DELETE SET NULL` 可空 + index;`code_enc Text` 可空(仅 `kind='user'`)。部分唯一索引 `uq_invite_codes_owner_active ON invite_codes(owner_user_id) WHERE revoked_at IS NULL AND owner_user_id IS NOT NULL`(模型里用 `Index(..., unique=True, sqlite_where=…, postgresql_where=…)`,保证 `test_models_match_migrations` 两边一致)。`invite_redemptions(id PK, code_id FK invite_codes.id NOT NULL + index, user_id FK users.id ON DELETE SET NULL 可空 UNIQUE, redeemed_at)`。
- **R-I2 码生成**:`services/invites.generate_code()` = 10 个字符取自 `ABCDEFGHJKMNPQRSTVWXYZ23456789`,`secrets.choice`,显示 `XXXXX-XXXXX`;`admin/invites.new_code` 改为调用它(管理员单个创建也用新格式)。哈希不变(`hash_code` = SHA-256(`normalise`))。
- **R-I3 兑换**(`redeem(session, app, code, now) -> InviteCode | RedeemError`,不提交):按哈希取行 → 不存在 / 已撤销 / 已过期 → `invalid`;`kind='user'`:所有者为空或被停用 → `invalid`,上限 `cap = quotas.effective(session, app, owner_id, "invites_user_code_max_uses")`;`kind='admin'`:`cap = row.max_uses`;`cap <= row.uses` → `used_up`;原子 `UPDATE … SET uses = uses + 1 WHERE id = :id AND revoked_at IS NULL AND uses < :cap`,`rowcount == 0` → `used_up`(并发)。错误映射:`invalid` → `403 {"error":"Invalid invite code"}`(现有文案);`used_up` → `403 {"error":"Invite code used up"}`(spec 要求提示「已用完」;这会让「码存在」可区分,接受,INDEX §9 第 7 条)。旧的 `consume()` 保留为 `redeem` 的薄包装(返回 bool),直到本计划 S4 改完调用方后删除。
- **R-I4 注册事务**(扩展 F 计划 R-F7):邀请模式下,`redeem` 与新用户、身份、`invite_redemptions` 同一事务;任何后续失败回滚,次数还回去。`INVITE_CODE` 环境单码 → 不写归属(没有码行)。`open` 模式忽略邀请码(X20)。被邀请者的 `user_id` 唯一,天然保证一人一条。
- **R-I5 按 IP 的邀请码错误计数**:`app.state.invite_fail_limiter = RateLimiter(settings.invite_failures_per_ip_hourly, window=3600)`;每次 `invalid` / `used_up` 记一次;**注册请求带了邀请码且该 IP 已达上限** → 直接 `429 "Too many requests, please try again later"`(不再查码,避免继续试);hub 监听热改。默认 5 次 / 小时。
- **R-I6 用户码资格**(`user_invites.eligibility(user, now, settings, cap)`):注册满 `invites_user_min_account_days`(默认 7)天;`email_verified_at` 非空;未停用;`cap > 0`(按人覆盖为 0 = 收回邀请权)。不满足 → `GET /api/me/invite` 返回 `{"eligible": false, "reason": "too_new"|"email_unverified"|"disabled_by_admin", "available_at": ISO 或 null}`(`too_new` 时给出可生成的时刻)。生成动作每用户每天 5 次(进程内限流,覆盖「生成 + 更换」)。
- **R-I7 用户码的生成与查看**:`POST /api/me/invite` 幂等:已有有效码就返回它(解密 `code_enc`);没有就生成(哈希唯一冲突重试 5 次)。`code_enc` 用 `secretbox.box_for(settings)`;**没有 `SETTINGS_ENCRYPTION_KEY` 时用户码功能不可用**(`503 "Invites are not configured"`),与 INDEX X9 一致。解密失败(换过加密钥)→ 视为无码,提示用户「更换」。
- **R-I8 更换**:`POST /api/me/invite/rotate {"confirm": true}` = 同一事务撤销旧码(`revoked_at = now`、`code_enc = NULL`)并生成新码;**新码的 `uses` 继承旧码的 `uses`**——spec 的「累计使用上限」按人累计,更换只是换一个字符串,不会多给次数(否则每天更换 5 次就能把上限放大 5 倍)。这样上限检查仍是单行原子更新(R-I3),不需要跨行求和。要多给次数只能由管理员调大配额覆盖。更换计入每日 5 次限流。管理员更换 / 撤销走管理端(S7);管理员**撤销**后用户再生成的新码同样继承累计数。
- **R-I9 面板数据**:`GET /api/me/invite` → `{eligible, code?, uses, cap, invitees: [{display_name, joined_at}]}`(只含昵称 / 用户名回落,不含邮箱、id;按兑换时间倒序,最多 50 条);`uses` 是累计数(R-I8),`invitees` 列出该用户**所有**用户码(含已更换的)的兑换者。生成新码时 `uses` 取「该用户所有用户码 `uses` 的最大值」(即上一个码继承下来的累计数)。
- **R-I10 管理端**:
  - `POST /api/admin/invites/batch {count 1–100, label, expires_at?}`(operator)→ `201 {"invites":[…], "codes":[…]}`(`no-store`;审计一条 `invite.batch_create`,`after={"count": n, "expires_at": …}`,`summary` 为标签);每个码 `kind='admin'`、`max_uses=1`。
  - `GET /api/admin/invites?kind=admin|user&owner=<用户名或 id>&state=…`:每行加 `kind`、`owner {id, username, nickname}`、`redeemers`(最多 5 个用户名 + 总数)。
  - `GET /api/admin/invites/{id}/redemptions`(operator):兑换者 `user_id / username / nickname / redeemed_at / disabled`。
  - `GET /api/admin/users/{id}/invite`(operator):该用户当前码的状态(`uses / cap / created_at / revoked_at`,**不含码**)、历史码数、累计兑换数、**被停用的被邀请者数**;`POST /api/admin/users/{id}/invite/revoke`、`POST /api/admin/users/{id}/invite/rotate`(operator,`ReasonIn`,审计 `invite.user.revoke` / `invite.user.rotate`,不返回新码——管理员不需要看到用户的码,用户自己在面板看)。
  - 配额覆盖沿用 `PUT /api/admin/users/{id}/quotas/invites_user_code_max_uses`;operator 能设的上限沿用现有 `operator_ceiling` = 站点默认 × `OPERATOR_FACTOR`(10,已核对)= 100,超过需 superadmin + step-up + 原因;不需要改 `OPERATOR_CAP`。
- **R-I11 删除用户**:其用户码撤销、`code_enc` 清空、`owner_user_id` 置空(`ON DELETE SET NULL` + `delete_user` 里显式撤销);其兑换记录 `user_id` 置空(`USER_REFS_NULLED`);审计不含码。
- **R-I12 分享链接**:`${location.origin}/register#invite=XXXXX-XXXXX`;分享优先 `navigator.share`(无则复制到剪贴板);分享文案不含个人信息。
