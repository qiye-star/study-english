# 对话增强:语音消息 + 发音评测 + 语法检查 + 双语 + 一键加入跟读(设计文档)

日期:2026-10-05(修订:加入自动语法检查模型与"语音与文字同时发出"的流程)
范围:`web/`(对话页、跟读页、查词抽屉)与 `server/`(消息关联评测/语法、语法接口、练习清单)。基于[手机网页版设计](2026-10-04-mobile-web-practice-design.md)。

## 1. 需求与我的判断

用户的要求:
1. 对话里增加内容:中英对照的一键翻译;可以把句子加入跟读练习。
2. 语音输入不再是"语音转文字填进输入框",而是**把语音和转出的文字同时发出去**:语音拿去打分,文字用来开始回答问题;对话和练习合在一个模块里。
3. **新增一个模型,指出用户的语法错误。**

**我的判断(不迎合):**

- **语音不直接喂给对话大模型。** 对话用的 DeepSeek 听不了音频;方舟 2.0-lite 能听,但它对发音的评判不稳定、不可复现。用户要的是"保留我说的话、知道说得怎么样、AI 照常回答"——发音分数交给讯飞评测(确定性、有词/音素级结果),对话只吃文字。
- **"同时发出去"在实现上是:一次录音 → 先转写 → 转写文字(给 AI 回答)和录音(给讯飞评测)并行发出。** 评测必须有参考文本,而参考文本就是转写结果,所以转写必须先完成;这是唯一的先后依赖。转写完成的那一刻,用户的气泡就带着文字出现,AI 开始回答,发音分数和语法反馈随后异步补上。
- **自由说话的发音评测不如跟读准确**:转写大模型可能把读错的词自动改对(评测会抓到不一致),也可能忠实写成错词(评测会给高分、漏掉)。所以对话里的分数定位成"发音提示",要精确打分走跟读页。设计里要求用真实录音实测并如实记录。
- **语法检查有一个天然盲区**:转写大模型同样可能把语法错误悄悄改对(例如把 "I goed" 写成 "I went"),语法模型就看不到错误。缓解:转写提示词已要求逐字转写;验收里要用故意说错语法的录音实测;气泡里展示转写文本,让用户看到"系统听成了什么"。这个限制必须写进验收记录,而不是假装不存在。语法模型必须忽略转写带来的标点/大小写差异和口语停顿词,否则全是误报。
- **不把跟读页并入对话页**:对话练"能不能说",跟读练"某一句读得准不准";按参考文本精确评分是最可靠的能力,不丢。整合方式是双向打通:对话里的句子(含语法模型给出的改正句)一键送去跟读;跟读页可先听范读。

## 2. 功能设计

### 2.1 语音消息
- 输入栏麦克风:点一下开始、再点一下结束并**自动发送**(录音中有"取消"丢弃按钮)。上限 60 秒。文字输入保持不变。
- 发送流程(客户端编排,复用现有接口):
  1. 录音 → 16 kHz 单声道 WAV(现有模块)。
  2. `POST /api/ai/audio/transcriptions` 得到转写文本。失败则气泡标红、保留录音,可"重试转写"。
  3. **转写完成立即**:用户气泡显示"录音 + 转写文本";转写文本作为用户消息走现有流式对话,AI 开始回答。
  4. **并行**:(a)`POST /api/speech/assessments`(`reference`=转写文本,`save=true`,`source=chat`)→ 发音分数徽标,转写里读得差的词变色;(b)`POST /api/ai/grammar`(见 §2.4)→ 语法徽标。
  5. 回复成功后保存消息对(现有逻辑);评测与语法结果通过 `PATCH /api/messages/{id}` 在到达时补写到用户消息上(它们可能晚于消息对保存到达)。
- 非英文转写(以中文为主):跳过评测和语法检查,气泡标注"未评测(非英文)",仍照常对话。
- 语音气泡:录音时长 + 回放 + 转写文本(高亮读差的词)+ 发音分数徽标 + 语法徽标;点开展开详情(复用评测结果视图 + 语法问题列表),有"跟读这句"。
- 上传两次(转写一次、评测一次,60 秒约 2 MB × 2):v1 接受;若实测移动网络下延迟不可接受,再改为服务端一次上传、内部编排。

### 2.2 自动语法检查(新增的"指出语法错误"的模型)
- 对**每条英文用户消息**(文字或语音转写)自动检查,与 AI 回答并行,不阻塞对话;少于 3 个单词或非英文则跳过。会话设置里可关闭("语法检查",默认开)。
- 结果显示为用户气泡下方的徽标:`语法 ✓`,或 `N 处语法问题`;点开列出每处:原文片段 → 改正 → 类别 → 中文简短说明,以及**整句的改正版本**,改正句带"跟读这句"和"收藏"。
- 缓存:同一文本的结果缓存到 IndexedDB;消息保存后,结果也持久化到服务端(重新打开对话仍能看到,不重复花钱)。

### 2.3 中英对照翻译
- 每条 AI 回复有"译"按钮:点击在原文下方显示中文(目标语言取"我的"页语言设置),再点收起。用现有 `translateText`(带缓存),不写服务端。
- 对话顶栏"双语"开关(默认关):打开后新回复流式结束自动翻译一次。用户自己的消息不自动翻译。

### 2.4 语法模型的服务端形态
- **新接口 `POST /api/ai/grammar`**(登录 + 用户级限流,同 `/api/ai/*`):`{ "text": "...", "context": "上一句 AI 的话(可选,≤500 字符)" }`。服务端用**固定的系统提示词 + JSON 模式**调用语法模型,校验并规整输出后返回,客户端不能借此改提示词。
- **模型配置**:新增 `GRAMMAR_MODEL`(默认等于 `DEFAULT_LLM_MODEL`),以及可选的 `UPSTREAM_GRAMMAR_BASE_URL` / `UPSTREAM_GRAMMAR_KEY`(留空则复用 LLM 上游)。这样"新增一个模型"既可以只是同一上游的另一个模型,也可以换成别家。
- **输出结构(服务端校验后)**:`{"has_errors": bool, "corrected": "整句改正", "errors": [{"original": "...", "corrected": "...", "category": "tense|agreement|article|preposition|word_choice|word_order|plural|spelling|other", "explanation": "中文说明"}]}`;`errors` 最多 8 项;`original` 必须出现在输入文本里(否则丢弃该项);无错误时 `has_errors=false`、`errors=[]`、`corrected` 等于原文。
- **提示词要点**:学习者口语转写;忽略标点/大小写/口语停顿词(uh、um)/自我修正造成的差异;只指出语法与用词错误,不评价风格;说明用中文且简短;输出严格 JSON。
- 错误处理:上游 401/403 → 502(沿用现有助手);非 JSON/结构非法 → 502 `Upstream unavailable`,不泄露上游内容;超长文本 413(`text` ≤ 2000 字符)。

### 2.5 一键加入跟读与练习清单
- AI 回复按句拆分;"跟读"面板列出各句,每句有"练"(跳到跟读页,参考文本预填)和"收藏"(加入练习清单)。查词抽屉在选中一句/一段时同样提供"跟读 / 收藏"。
- **练习清单**:跟读页入口,条目可点进跟读、可删除;来源记为 chat / lookup / grammar / manual。
- 跟读页新增"先听范读"(现有 TTS)。

### 2.6 教练模式(可选,默认关)
- 打开后,系统提示词附加"学习者上一句可能读错的词:X、Y(发音分 N)/ 语法问题:…",让 AI 自然重述(recast),不打断对话。(依赖评测/语法结果先到达;未到达则本轮不附加。)

### 2.7 明确不做(v1)
- 把音频直接喂给大模型做点评;实时语音/打断式对话;角色扮演场景模板、建议回复;多语言评测;服务端一次上传内部编排(见 §2.1,有实测证据再做)。

## 3. 服务端数据与接口(迁移 `0004`)
- `messages` 增加可空列:`assessment_id`(指向 `assessments.id`,评测被删除时置空;写入时校验属于当前用户)、`grammar`(JSON,语法结果)。`message_out` 返回这两个字段。`POST /api/conversations/{id}/messages` 的单条消息可带它们;新增 `PATCH /api/messages/{id}`(只允许改这两个字段,按用户隔离,越权 404,`grammar` 经同一校验)。
- `assessments` 增加 `source`(`practice`|`chat`,默认 `practice`);`POST /api/speech/assessments` 接收可选表单字段 `source`;`GET /api/assessments` 默认只列 `practice`,可用 `?source=chat|all` 筛选。
- 删除对话/消息时,级联删除其关联的 `source=chat` 评测及录音文件(避免孤儿文件吃配额),有测试。
- `POST /api/ai/grammar`(§2.4);配置项 `GRAMMAR_MODEL`、`UPSTREAM_GRAMMAR_BASE_URL`、`UPSTREAM_GRAMMAR_KEY`;`/api/config` 不暴露这些。
- 新表 `practice_items`:`id`(uuid)、`user_id`、`text`(≤ 2000)、`source`、`created_at`;`GET/POST /api/practice-items`、`DELETE /api/practice-items/{id}`;每用户上限 `MAX_PRACTICE_ITEMS`(默认 500,超限 429);相同文本去重(返回已有项)。
- 配额沿用 `RECORDING_QUOTA_MB`(对话录音同样计入;60 秒 ≈ 1.9 MB)。

## 4. 网页端设计
- 复用:录音/WAV 模块、评测结果视图、`translateText`、TTS 播放器、查词抽屉、统一错误翻译。
- 新增:`useVoiceTurn`(编排:录音→转写→对话+评测+语法,含取消/重试/卸载清理,麦克风释放)、语音气泡、发音与语法徽标及详情、句子拆分与跟读面板、练习清单页与 API、语法 API 封装与缓存、会话设置项(语法检查、教练模式、双语默认)。
- 移动优先:录音/取消按钮 ≥ 44 px,键盘与安全区沿用现有布局;文案 en + zh-CN。

## 5. 风险与未验证项
- **自由说话评测与语法检查的盲区**(见 §1):必须用真实录音实测并记录——故意读错的词、故意说错的语法各若干句;看转写是否悄悄改对。结果写进验收记录;若盲区严重,降级方案:语法检查只对"文字输入"生效,语音消息只给发音提示。
- **延迟与成本**:每轮语音 = 方舟转写 + 讯飞评测 + DeepSeek 回复 + 语法模型(+ 可选 TTS/翻译)。讯飞评测的并发/配额我没有核实,实测时观察;评测与语法调用沿用用户级限流。
- **iOS Safari 录音**仍未真机验证;真机清单追加"语音消息""语法徽标"项。
- 语法模型的误报会打击学习者信心:提示词与服务端校验尽量保守(只报确定的错误),验收里用一组"本来正确"的句子检查误报。

## 6. 验收标准
1. 服务端:迁移 `0004` 在 SQLite/Postgres 通过;`assessment_id`/`grammar` 的校验与越权、`PATCH` 隔离、级联删除(行+文件)、`source` 筛选、`/api/ai/grammar`(限流、校验、`original` 必须出现在输入、畸形上游输出、上游 401/403 映射、超长 413)、练习清单(上限/去重/隔离)均有测试;现有 390 项不受影响。
2. 网页端:`tsc`、单元测试、`vite build` 通过;语音消息的取消/转写失败重试/卸载释放麦克风、评测/语法晚到补写(PATCH)有测试。
3. 真实上游端到端(Chromium 手机预设,假麦克风):语音消息 → 气泡显示转写 → AI 流式回复 → 发音徽标出现 → 语法徽标出现(用一条故意带语法错误的文字消息和一条正确消息分别验证);气泡回放;改正句"跟读"带参考文本跳转;翻译与缓存;收藏→清单→跟读;删除对话后评测与录音文件消失。WebKit 项目跑非录音用例,录音用例按规则跳过并写明原因。
4. 自由说话评测与语法检查的实测记录(含误报检查);真机项标注未验证。

## 7. 阶段(详细计划另写)
1. 服务端:迁移 `0004`、消息关联评测/语法与 `PATCH`、`source`、级联删除、练习清单、`/api/ai/grammar` 与配置。
2. 网页:翻译(单条+双语开关)、句子拆分与跟读面板、练习清单页、跟读页"先听范读"、查词抽屉的"跟读/收藏"。
3. 网页:语音消息(`useVoiceTurn`、语音气泡、发音徽标与详情、取消/重试)。
4. 网页:语法检查(徽标、详情、改正句跟读/收藏)、教练模式、会话设置项。
5. 端到端、自由说话与语法的实测、真机清单更新、文档。
